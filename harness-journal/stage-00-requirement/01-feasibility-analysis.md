## 执行内容

用户提出："使用前后端数据库+langgraph可插拔式能实现吗这个平台"

梳理后的核心需求：
1. **平台定位**：元应用平台，用户输入需求 → Agent 按 Harness 流程生成可部署应用
2. **技术要求**：前端 + 后端 + 数据库 + LangGraph（可插拔）
3. **Harness 角色**：作为平台的"引擎层"，用户看到的是"输入需求→得到应用"，背后跑的是完整 Harness 流程

### 可行性判断结论：能实现，且 LangGraph 是当前最匹配的选择

Harness 流程与 LangGraph 设计模型的高度吻合点：

| Harness 概念 | LangGraph 对应 |
|-------------|---------------|
| 8 阶段流程 | Graph 的 Node 序列 |
| 决策菱形（通过?/失败?） | Conditional Edge |
| 反馈循环（失败→修复→重跑） | Graph Cycle（环） |
| Agent 专业化（架构师/开发/审查） | 不同 Node 实现 |
| 持久化记忆（progress.txt/feature_list） | Checkpointer + Database |
| 人工介入（暂停/审批） | Human-in-the-loop interrupt |
| 上下文按需检索 | Node 内部调用检索工具 |
| 约束层注入 | State 中携带约束数据，每个 Node 读取 |

"可插拔"是 LangGraph 的天然特性——每个 Node 是一个函数，可替换实现而不改 Graph 拓扑。

### 风险识别

| 风险 | 难度 | 说明 |
|------|------|------|
| 代码执行沙箱 | ★★★★ | Agent 要跑 mvn verify/git/测试套件，需 Docker 隔离 |
| 长时运行 Agent | ★★★★ | 一个项目可能跑几小时，需处理超时/重试/资源回收 |
| LLM 输出稳定性 | ★★★★ | 约束层必须足够严格才能兜住 |
| 实时状态推送 | ★★★ | 需在 Node 执行后通过 SSE 推给前端 |
| Git Worktree 管理 | ★★★ | 并行 Agent 各需独立分支 |
